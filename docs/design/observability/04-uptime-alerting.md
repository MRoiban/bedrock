# Uptime, jobs, alerting and status

Research checked 2026-11-07. Numbers below are proposed home-server defaults, not experimentally validated thresholds. Links distinguish existing behavior from recommendations.

## 1. Recommendation

- **Build a small evaluator into the daemon, not another monitoring stack.** Reuse supervision, proxy measurements and SQLite; keep notification policy/transport in comms. Bedrock already health-gates swaps, retries crashes, and considers idle/intentionally stopped pebbles normal. Preserve these semantics. Read-only grounding: [architecture](/home/jarvis/.bedrock/src/ARCHITECTURE.md), [reference §§8,10,11,13,14](/home/jarvis/.bedrock/src/docs/reference.md:636), [author guide](/home/jarvis/.bedrock/src/packages/bedrock/AGENTS.md:619).

- **Separate process liveness, readiness and application correctness.** Keep the existing private `/_bedrock/health` for launch compatibility; it currently returns metadata, not a database or dependency test. Add bounded readiness over IPC: migrations complete, local DB readable, required services started, accepting work. Report `starting|ready|degraded|failed|idle|stopped`; exclusive services can be unavailable after activation, so launch health alone is insufficient. An optional application check should declare only essential dependencies, with a 2-second deadline; never recursively call every upstream. [Current health implementation](/home/jarvis/.bedrock/src/packages/bedrock/src/runtime/index.ts:77), [service handoff contract](/home/jarvis/.bedrock/src/docs/reference.md:1330).

- **Probe locally every 30 seconds**, timeout 2 seconds, max concurrency 2, no overlap; open after 3 failures and resolve after 2 successes. Do not wake idle pebbles for routine checks: use registry state; label them available-on-demand, not tested-ready. Allow one explicitly selected end-to-end canary to wake. Copy Gatus's separate failure/recovery thresholds rather than alerting on individual samples. [Gatus configuration](https://github.com/TwiN/gatus#configuration).

- **Expose one deliberately public canary**, proposed `GET https://bedrock.<domain>/healthz`: exact 200 plus a small versioned marker only when the daemon loop and bounded registry read work; 503 otherwise. Set `Cache-Control: no-store` and a Cloudflare cache bypass; reject login redirects and unexpected bodies in the prober. No names, counts, errors, tokens or logs. This tests DNS/TLS/edge/tunnel/daemon; add a nominated pebble canary only if application readiness matters. A healthy tunnel does not prove application health. [Cloudflare warning](https://developers.cloudflare.com/tunnel/observability/), [Upptime body/status checks](https://upptime.js.org/docs/configuration/).

- **Free external coverage, with explicit opt-in:** first enable Cloudflare **Tunnel Health Alert → owner email**, available on all Zero Trust plans. It runs outside the home failure domain and sends without comms. It is connector monitoring, not HTTP probing; standalone **Health Checks are not Free** (0 checks). This is useful baseline coverage using an existing provider, not complete uptime monitoring. [Tunnel notifications](https://developers.cloudflare.com/notifications/notification-available/), [Health Checks availability](https://developers.cloudflare.com/health-checks/#availability).

- **For real free HTTP probing, recommend opt-in Upptime on GitHub-hosted runners**, public minimal repository, standard runners, schedule `2-57/5 * * * *`. Probe only the canary; use a small wrapper/custom workflow to require 3 failed observations across runs and 2 successes before recovery, persist state in the repository, serialize runs. Nominal detection is approximately 10–15 minutes; scheduling delays mean no guaranteed bound. Send outage notices independently through GitHub issue email subscriptions or external provider credentials, never exclusively through home-hosted comms. Public standard runners are free; private-repository allowances differ. [Upptime design](https://upptime.js.org/docs/), [billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions), [scheduling caveats](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

- **Who watches that watcher?** Optionally let each completed external probe run ping a hosted Healthchecks.io check (period 5 minutes, grace 15 minutes), regardless of target success: this detects a stalled prober, not the target. Alternatively, daemon heartbeat every minute/grace 4 minutes detects host/daemon/outbound loss, but cannot establish inbound reachability. Free hosted Healthchecks currently allows 20 checks; sending only an opaque heartbeat minimizes disclosure. No external SaaS is enabled automatically. With none accepted, document that whole-box failure detection is unavailable; a monitor on that box cannot solve it. [Dead-man's-switch model](https://healthchecks.io/docs/), [pricing](https://healthchecks.io/pricing/).

- **Persist bounded monitoring state in daemon SQLite:** `checks(id,target,kind,policy,state,last_observed_at,next_due_at)`, `incidents(id,fingerprint,opened_at,resolved_at,ack_at,last_notified_at)`, `silences(match,until,reason)`, `notification_outbox(id,incident_id,payload,next_attempt_at,comms_id)`. Keep raw probes 7 days, minute counts 30 days, daily aggregates/incidents 365 days; cap raw history at 100,000 rows and outbox at 1,000 pending messages, compact repeated updates on overflow and retain incident state. Store every transition; aggregate routine successes. These are proposals inspired by [Kuma's transition logic](https://github.com/louislam/uptime-kuma/blob/master/server/model/monitor.js#L1327) and [Alertmanager routing](https://prometheus.io/docs/alerting/latest/configuration/).

- **Instrument jobs at the execution boundary.** Emit `scheduled,started,succeeded,failed,skipped_overlap,interrupted` events with `run_id`, scheduled occurrence, actual start/finish, release and hinted error code. Persist job history in the pebble DB and forward compact IPC events to daemon history; missing completion after process death is `interrupted/unknown`, never presumed success. Transactional success means after commit; detached success means the handler resolved, not proof that an external side effect happened exactly once. Keep 30 days/10,000 runs per pebble, whichever limit first. Existing jobs log failures, skip overlap, and have no persisted history/catch-up. [Scheduler source](/home/jarvis/.bedrock/src/packages/bedrock/src/jobs/index.ts), [Cronitor run correlation](https://cronitor.io/docs/telemetry-api).

- **Monitor expected completion, not just errors.** Daemon retains cron/timezone/release metadata and computes due occurrences independently of the child. On restart, reconcile missed occurrences as one gap incident, without replay. Preserve server-local cron/DST behavior initially and store actual occurrence timestamps. Default start grace 5 minutes; runtime budget 10 minutes until explicitly set; flag budget expiry as overdue, without killing the job. For irregular schedules, compare actual scheduled occurrences rather than `2 × last interval`. Overlap is a recorded skip and can cause a missed-completion incident. Start/fail/success and grace are established designs. [Healthchecks configuration](https://healthchecks.io/docs/configuring_checks/), [runtime monitoring](https://healthchecks.io/docs/measuring_script_run_time/), [Bedrock cron contract](/home/jarvis/.bedrock/src/docs/reference.md:1182).

- **Ship only a few actionable alerts.** Default: prolonged public unreachability; desired-running pebble not ready for 2 minutes or supervisor entering `crashed`; an explicitly critical job failing/missing its deadline; no successful backup for >2× configured interval; critical notification delivery unavailable >10 minutes. Ordinary job errors enter the digest; repeated failures escalate only for jobs the owner marks critical. Include observed duration, last success and a repair command. Single crashes, CPU/memory spikes, isolated 5xx and browser errors are records, not pages. Backup-age semantics already exist in [doctor](/home/jarvis/.bedrock/src/docs/reference.md:894); actionable-only policy follows [PagerDuty guidance](https://www.pagerduty.com/resources/digital-operations/learn/alert-fatigue/).

- **Deduplicate and group before comms.** Fingerprint `host/pebble/rule/job` without timestamps, request URLs or release IDs; one incident per episode. Group related incident transitions for 30 seconds; send changes at most every 5 minutes. Inhibit child-unreachable notifications under a confirmed host/tunnel incident, retaining evidence; do not suppress unrelated known data failures. Persist maintenance silences with reason/expiry, default 1 hour; acknowledgment stops reminders but does not imply recovery. [Alertmanager grouping, inhibition and silences](https://prometheus.io/docs/alerting/latest/alertmanager/).

- **Use comms's actual API and routing.** Register a dedicated `bedrock-monitor` client; protect its token in daemon configuration, not child environments. `POST /api/v1/messages` with `to:["me"]`, `subject`, `text`, `urgency`, `idempotency_key`, `metadata:{incident_id,rule,target}`. `high` defaults to ntfy + Poke, `normal` to Poke, `low` to email. Mark excerpts from untrusted requests `untrusted:true`; exclude payloads/credentials. Existing contract: [comms API and client helper](/data/t3/projects/comms/docs/agents.md:101).

- **Make enqueueing durable; don't duplicate provider retry machinery.** Commit incident + outbox together; dispatch outside SQLite transactions. Retries reuse an immutable payload/key `bedrock:<incident>:<transition>:<sequence>`; changed payloads need new keys. Comms returns queued/duplicate, then exposes per-channel outcomes: acceptance is not delivery or acknowledgment. Follow its message ID; retry submission on network/429/5xx with jitter and `retry_after_ms`, stop permanent auth/config failures. Comms already retries providers at 1m,5m,30m,2h,6h,12h and guarantees at-least-once, not exactly-once. [Existing behavior](/data/t3/projects/comms/docs/agents.md:153).

- **Escalate channels, not imaginary teammates.** Proposed: normal outage → Poke; unresolved/unacknowledged after 15 minutes → ntfy + email once; then at most one reminder/6 hours. Data-loss-imminent critical incidents can use `high` immediately. Comms already defers normal/low push during **23:00–07:30 Europe/Brussels**, but high and email bypass quiet hours. Bedrock must also defer noncritical escalation during that window. Default home outages should not wake the owner. Monitor comms `/health` plus oldest delivery age; test a real delivery monthly. Whole-host fallback must remain external. [Routing/quiet hours](/data/t3/projects/comms/docs/agents.md:159), [health endpoint](/data/t3/projects/comms/docs/agents.md:250).

- **Weekly email by default; daily only when unhealthy or requested.** Monday 08:00 local: unresolved incidents, missed/failed critical jobs, backup age, availability with observation coverage, noisy rules, failed notifications and repair links. Daily 08:00 summarizes actionable unresolved items; no routine success mail or per-job completion mail. A page means an interrupting notification, distinct from a dashboard/webpage. [PagerDuty's operational recommendations](https://docs.pagerduty.com/ops-guides/auto-remediation/automation-for-resolution).

- **Provide private status and optional external public status.** Extend `bedrock status --json`; add `bedrock jobs history <pebble> --json`, `bedrock alerts ls|ack|silence|test --json` and authenticated `/api/alerts`, `/api/checks`, `/api/jobs/<pebble>/history`; preserve Bedrock envelopes/hints. Public status should be an opt-in, redacted GitHub Pages page generated from external observations, with components, maintenance, incidents and `last_checked_at`; stale data becomes **unknown**, never green. Mark intentional downtime and observation gaps separately; no raw logs, users or private pebble names. Home-hosted status is diagnostic only during a box outage. [Agent contract](/home/jarvis/.bedrock/src/ARCHITECTURE.md:161), [Upptime Pages model](https://upptime.js.org/docs/).

- **Defer burn-rate paging until traffic supports it.** Optional 30-day 99.9% request SLO: burn = bad-request fraction / 0.001; alert when **both** 1h and 5m exceed 14.4, **or both** 6h and 30m exceed 6. Slower 1× over 3d and 6h goes to digest. For sparse home traffic, use synthetic checks; an optional request-rule minimum of 100 requests per evaluated window reduces noise but can hide low-volume failures. Zero requests is unknown. Keep probe availability separate from request SLOs. [SRE Workbook, including low-traffic caveats](https://sre.google/workbook/alerting-on-slos/).

## 2. Sources studied

- **Uptime Kuma:** self-hosted probes, push monitors, notifications and status pages. Copy pending/retry states and transition-based notification; avoid running the only watcher/status page on its target. Source explicitly distinguishes important beats from notification-worthy transitions: [README](https://github.com/louislam/uptime-kuma), [monitor code](https://github.com/louislam/uptime-kuma/blob/master/server/model/monitor.js#L1327).
- **Gatus:** declarative conditions, separate failure/success thresholds, maintenance and SQLite storage. Copy compact reproducible policy; avoid its default in-memory history for persistent incidents. Configuration growth is a tradeoff, not evidence of product failure. [README/storage/alerting](https://github.com/TwiN/gatus#storage).
- **Healthchecks.io / healthchecks:** open-source Django service; expects scheduled pings, recognizes late/down and start/success/fail. Copy deadlines and dead-man's-switch monitoring. A heartbeat proves reported activity, not inbound availability; local hosting shares the target's failure domain. [Design](https://healthchecks.io/docs/), [source](https://github.com/healthchecks/healthchecks), [reliability tips](https://healthchecks.io/docs/reliability_tips/).
- **Cronitor:** commercial job/heartbeat/site monitoring. Copy run IDs/`series`, explicit completion and grace/failure tolerance; avoid treating heartbeat ticks as completed work or assuming one tolerance applies to all assertions. [Lifecycle](https://cronitor.io/docs/cron-job-monitoring), [API distinctions](https://cronitor.io/docs/monitors-api).
- **Statping-ng:** Go status monitoring with multiple database backends including SQLite. Copy component status/public communication and its explicit instruction to host status separately from the monitored instance; avoid the shared-failure deployment its README warns against. [README](https://github.com/statping-ng/statping-ng).
- **Upptime:** Actions probes, Issues incidents, Pages status. Copy external failure-domain separation and cheap public status; avoid assuming cron precision, default instant incident creation, or deletion of brief incidents is an audit trail. [Design](https://upptime.js.org/docs/), [notification secrets](https://upptime.js.org/docs/notifications/), [GitHub limits](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- **Prometheus Alertmanager:** routes, groups, deduplicates, inhibits and silences alerts. Copy these concepts in a bounded SQLite evaluator; avoid a full routing DSL or deploying Prometheus merely to deliver a few notifications. [Concepts](https://prometheus.io/docs/alerting/latest/alertmanager/), [timing configuration](https://prometheus.io/docs/alerting/latest/configuration/).
- **Grafana OnCall OSS:** incident response/escalation design worth studying, not a new dependency. README says maintenance began 2025-03-11 and archival 2026-03-24; the moved cold-storage repository also displays an archive date of June 5. Copy explicit acknowledgment/escalation; avoid new reliance on retired software. [Archived repository](https://github.com/grafana-cold-storage/oncall), [vendor announcement](https://grafana.com/blog/2025/03/11/grafana-oncall-maintenance-mode/).
- **PagerDuty:** its 2022 research reports 54% of responders interrupted outside normal working hours; enterprise survey/platform evidence does not estimate this owner's burden. Copy measuring interruptions and regularly removing non-actionable rules; avoid generic alert-volume marketing statistics as design targets. [Study](https://www.pagerduty.com/state-of-digital-ops-2022/), [alert-fatigue guidance](https://www.pagerduty.com/resources/digital-operations/learn/alert-fatigue/).
- **Google SRE Workbook:** compares precision, recall, detection/reset time and increasingly sophisticated SLO alerts. Copy paired windows and low-traffic caution; avoid transplanting high-volume service policies unchanged. [Chapter 5](https://sre.google/workbook/alerting-on-slos/).
- **Cloudflare:** free Tunnel notifications offer useful off-box detection; paid standalone Health Checks add configurable probes. Copy existing infrastructure coverage, but distinguish connector state from user-facing success. [Tunnel observability](https://developers.cloudflare.com/tunnel/observability/), [plan matrix](https://developers.cloudflare.com/health-checks/#availability).

## 3. Anti-patterns

- **A green tunnel or local dashboard proves uptime:** Cloudflare explicitly warns otherwise; require external application observations and a delivery route independent of the target. [Evidence](https://developers.cloudflare.com/tunnel/observability/).
- **“Free Actions cron is a reliable clock”:** scheduled runs may be delayed/dropped; public repos lose schedules after 60 inactive days. Upptime's routine commits help with activity but are not an independent watchdog. Add stale-state reporting and optionally the dead-man's switch. [GitHub documented failure modes](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- **Every error deserves a page:** produces desensitization and off-hours load. Group incidents, defer ordinary failures and inspect interruption counts weekly. [PagerDuty mechanism](https://docs.pagerduty.com/ops-guides/auto-remediation/automation-for-resolution), [research](https://www.pagerduty.com/state-of-digital-ops-2022/). PagerDuty also documents Etsy removing non-actionable resource alerts and holding weekly reviews: [operational case](https://www.pagerduty.com/blog/uncategorized/lets-talk-about-alert-fatigue-2/).
- **Notifications equal incidents:** comms idempotency prevents duplicate submissions, not repeated-condition alerts, acknowledgment or provider duplicates. Persist incident policy first; don't mistake a queued response for successful delivery. [Contract](/data/t3/projects/comms/docs/agents.md:153).
- **An exception logger detects missing jobs:** a dead scheduler emits no exception; persist expected deadlines. Do not introduce catch-up or exactly-once promises under the name of monitoring. [Existing scheduler](/home/jarvis/.bedrock/src/packages/bedrock/src/jobs/index.ts), [Healthchecks design](https://healthchecks.io/docs/).
